# Proposed matching review workflow

This is a proposal for the next small step, not an implemented replacement pipeline.

**Goal:** connect each interview to a scoring player, tournament edition, and completed round, with a human decision we can trace and preserve. Do this before building model features or training models.

## Keep three things separate

1. **Candidates — generated by code.** One row per source interview. Suggest a player/event/round only when the evidence identifies one choice. Ambiguous values stay blank, with an explanation; do not silently pick the closest name. Regenerating candidates is safe.
2. **Decisions — edited by you.** Record approve, reject, or needs-review, the confirmed event/player/round, reviewer name, and optional notes. A correction is an approval with the corrected IDs/round. Code must never overwrite this file. Missing decisions mean pending.
3. **Approved links — generated from decisions.** Export the confirmed source-to-score relationships. Check that the selected IDs and current round exist. Unresolved, conflicting, or stale decisions do not enter this export.

Keep the candidate suggestion visible even when corrected; your confirmed values belong in the decision file. This distinguishes what the program guessed from what a teammate approved.

## Proposed files and fields

| File | Who writes it | Key fields |
| --- | --- | --- |
| `matching/candidates.csv` | Program | source interview ID and URL, year, source player/event/date, proposed scoring event/player/round, scoring names, match reason, evidence URLs, source fingerprint |
| `matching/decisions.csv` | Human reviewer | source interview ID, reviewed fingerprint, decision, confirmed event/player/round, reviewer, reviewed date, notes |
| `matching/approved_links.csv` | Program | source interview ID, confirmed event/player/round, year, source fingerprint, reviewer |
| `matching/issues.csv` | Program | source interview ID and reason a candidate/decision cannot be exported |

Use the source plus interview ID as the stable review key, and source-native scoring IDs to distinguish players and event editions. Names and dates are evidence, not primary keys. A fingerprint ties the decision to the exact source evidence reviewed. If that evidence changes, preserve the decision but flag it for re-review rather than silently accepting or deleting it. New years add candidates; they do not reset existing decisions. Reject duplicate/conflicting review keys explicitly.

These filenames describe the proposed interface, not files that already exist. We can simplify the columns before implementation.

## Matching is different from eligibility for prediction

An interview can be correctly linked to round 1 even if the golfer withdraws before round 2, or the event has an overnight delay. Preserve a human-approved identity/round link; separately report whether a valid next-round score exists and whether timing allows it to be a prediction example. Likewise, a final-round interview can have a correct match without a next-round target.

This avoids the pilot's ambiguity where "excluded" could mean either "could not identify the round" or "identified it, but cannot use it for this prediction task." No timing exception should silently become an eligible model example.

## Small implementation sequence, after agreement

1. Define the metadata input tables and implement candidate generation for one existing tournament. Use only the source-loading and matching essentials from the pilot.
2. Walk through a few candidates together and save your decisions. Validate corrections, rejection, ambiguous names/rounds, and reruns that preserve decisions.
3. Export approved links and a separate next-round eligibility report. Test that changing the year or rerunning collection cannot mix tournament editions or erase review work.
4. Add more tournaments and years once that workflow is comfortable. Agree as a team who collects sources, who reviews links, and who consumes the approved export.

The teammate-facing branch should eventually contain source loading, matching/review, focused tests, and a short README. Features, text-category rules, embeddings, and training remain in the pilot reference. No extraction or new matching code is included in this proposal commit.
